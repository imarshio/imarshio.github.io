## 一、设计模式

> 面试官问设计模式，通常就三连问：**是什么 → 你哪里用了 → 为什么用它而不是 if-else**。
> 每个模式都按这三问准备。

### 1. 注册表模式（Registry）

**是什么**：建一个全局的「登记处」（通常是一个字典），各个组件启动时把自己**登记**进去（名字 → 对象）；使用方只按名字去登记处**查**，不直接依赖具体组件。

可以理解为「电话簿」：你不需要认识每个人，只要知道名字就能查到电话。

**最小代码**：
```python
class ToolRegistry:
    def __init__(self):
        self._specs: dict[str, ToolSpec] = {}

    def register(self, spec: ToolSpec):          # 登记
        if spec.name in self._specs:
            raise ValueError(f"重复注册: {spec.name}")
        self._specs[spec.name] = spec

    def lookup(self, name: str) -> ToolSpec | None:   # 查找
        return self._specs.get(name)

    def all(self, predicate=lambda s: True):         # 按条件筛选
        return [s for s in self._specs.values() if predicate(s)]

GLOBAL_REGISTRY = ToolRegistry()
GLOBAL_REGISTRY.register(ToolSpec(name="search_chunks", parallel_safe=True, ...))
```

**项目里怎么用**：`core/agent/tools/registry.py` 的 `GLOBAL_REGISTRY`。每个工具是一个 `ToolSpec`（名字、参数 schema、处理函数、元数据），启动时全部注册。运行时：
- 给模型发工具列表 → 从注册表按 agent 权限筛选；
- 模型返回 tool_call → 按名字 `lookup` 拿到处理函数执行；
- 并行、延迟加载、打转检测 → 都是读 `ToolSpec` 上的元数据决定，**主循环里没有一行写死某个工具名**。

**为什么不用 if-else**：
```python
# 不用注册表：每加一个工具都要改主循环，100 多个工具就是 100 多个分支
if name == "search_chunks": ...
elif name == "web_search": ...
```
用注册表后，加工具 = 写一个 ToolSpec 注册进去，主循环零改动（**开闭原则：对扩展开放，对修改关闭**）。

**适合**：同一类东西很多、会持续增加、需要按名字动态查找（工具、插件、消息处理器、命令）。
**不适合**：只有两三个固定实现的场景，直接写反而清楚。

**常见追问**：
- 「和工厂模式什么区别？」注册表**存已有的对象**，按名字取；工厂**负责创建新对象**。两者经常一起用：注册表里存的是「名字 → 构造方法」，就成了工厂。我们的 `ToolSpec` 里存的是 `run_factory`，每次运行按会话上下文创建一个绑定了当前用户的处理函数 —— 这就是注册表 + 工厂的组合。
- 「Java 里对应什么？」Spring 容器本身就是一个巨大的注册表（Bean 名字 → Bean 实例）。

### 2. 工厂模式（Factory）

**是什么**：把「创建哪个具体类的对象」这个判断收到一个地方，调用方只说「我要什么」，不关心「怎么造」。

**最小代码**：
```python
_BACKENDS = {"openai": OpenAIBackend, "dashscope": OpenAIBackend, "anthropic": AnthropicBackend}

def backend_for(protocol: str) -> LLMBackend:
    cls = _BACKENDS.get(protocol)
    if cls is None:
        raise ValueError(f"不支持的协议: {protocol}")
    return cls()
```

**项目里怎么用**（两处）：
1. **模型后端**：`core/llm/backends/registry.py` 的 `backend_for(protocol)`。模型配置里写着协议（openai / anthropic / dashscope），工厂据此创建对应的后端。上层的 `LLMClient` 只调用 `backend.complete(...)`，不知道底下是哪家。
2. **文档解析**：`worker/pipeline/factory/`。上传文件后，按文件类型创建对应的解析流水线（PDF、Word、Excel、音频……近 20 种）。

**适合**：创建逻辑有分支、将来会加新类型、调用方不该知道具体类。
**不适合**：只有一种实现。

**追问**：「简单工厂、工厂方法、抽象工厂区别？」
- 简单工厂：一个函数 / 类按参数返回不同产品（我们用的就是这种）。
- 工厂方法：父类定义创建方法，子类决定创建什么。
- 抽象工厂：创建「一整套」相关产品（比如一套 UI 组件：按钮 + 输入框 + 弹窗，分 Windows 风格和 Mac 风格）。

### 3. 策略模式（Strategy）

**是什么**：同一件事有多种**算法**，把每种算法封装成独立的类，实现同一个接口，运行时按条件选一个。调用方只依赖接口。

**最小代码**：
```python
class Limiter(ABC):
    @abstractmethod
    def acquire(self, tokens: int) -> None: ...
    @abstractmethod
    def release(self) -> None: ...

class SlidingWindowLimiter(Limiter):     # 按每分钟请求数 / token 数限
    def acquire(self, tokens): ...       # Redis ZSet 滑动窗口

class ConcurrencyLimiter(Limiter):       # 按同时在跑的请求数限
    def acquire(self, tokens): ...       # Redis ZSet 信号量

def limiter_for(spec) -> Limiter:
    return {"window": SlidingWindowLimiter, "concurrency": ConcurrencyLimiter}[spec.limiter_kind](spec)

# 调用方
limiter.acquire(estimated_tokens)
try:
    resp = backend.complete(...)
finally:
    limiter.release()
```

**项目里怎么用**：模型限流。不同供应商的限流规则**本质不同**：百炼按每分钟请求数和 token 数（滑动窗口），DeepSeek、智谱按同时在跑的请求数（并发）。每种做成一个策略类，`LLMClient` 只调 `acquire / release`。

**一个经验（面试加分）**：不是所有「不同」都值得建策略类。
- **算法不同** → 建策略类（限流）；
- **只是数据不同** → 加配置字段就行（比如不同时段价格不同，只是价格表不同，计算方式一样）。
过度使用策略模式会让类爆炸。

**适合**：多种可互换的算法，且会扩展（支付方式、折扣规则、排序规则、限流算法、重试策略）。
**和工厂的关系**：工厂负责「选哪个策略并创建」，策略负责「具体怎么做」，经常一起出现。
**和 if-else 比**：if-else 把所有算法写在一个函数里，加一种算法就要改这个函数，还容易互相影响。

### 4. 适配器模式（Adapter）

**是什么**：两个接口对不上，中间加一层「转换头」，让旧的 / 外部的东西能按我们的接口使用。像电源转换插头。

**项目里怎么用**（两处）：
1. **Anthropic 协议适配**：系统内部统一用 OpenAI 的消息格式（`messages`、`tool_calls`、`role=tool`）。Claude 的格式不一样（system 单独传、工具结果是 `tool_result` 内容块、流式事件类型不同、思考块要原样回传）。`anthropic_backend.py` 负责双向转换：请求转出去、流式事件转回来。上层几十处代码都只认 OpenAI 格式，**零改动**接入 Claude。
2. **MCP 适配**：MCP server 的工具格式和我们内部的 `ToolSpec` 不同，`mcp_bridge.py` 把每个 MCP 工具包成一个 `ToolSpec` 注册进注册表，对运行时来说和内置工具没有区别。

**适合**：接入第三方 SDK / 老系统 / 外部协议，又不想让外部格式渗透到业务代码里。

### 5. 模板方法模式（Template Method）

**是什么**：父类定义一个流程的**骨架**（步骤顺序固定），某些步骤留给子类实现。

**项目里怎么用**：文档解析 `worker/pipeline/abstract_pipeline.py` 的 `BasePipeline`。所有格式的处理流程是一样的：下载文件 → 转成 markdown → 处理图片 → 切分 → 向量化 → 入库 → 更新进度；只有「转成 markdown」这一步每种格式不同。父类管流程和公共步骤（图片上传、进度通知），子类（`PdfPipeline`、`MsWordPipeline`、`AudioPipeline`……）只实现自己的解析。

```python
class BasePipeline(ABC):
    def run(self):                    # 骨架，子类不改
        md = self.parse()             # 留给子类
        md = self._upload_images(md)  # 公共
        chunks = self._split(md)      # 公共
        self._index(chunks)           # 公共

    @abstractmethod
    def parse(self) -> str: ...
```

**适合**：多个流程「大体相同、局部不同」。
**和策略的区别**：模板方法用**继承**，变化的是流程中的某一步；策略用**组合**，变化的是整个算法。

### 6. 责任链 / 兜底链（Chain of Responsibility）

**是什么**：请求沿着一条链依次传递，每个节点要么处理，要么交给下一个。

**项目里怎么用**：模型兜底链。主模型重试 3 次还失败 → 换配置里的第一个兜底模型 → 再失败换第二个 → 全部失败返回统一提示。链在配置中心配置，层数不限。

**适合**：多个处理者按优先级尝试（审批流、过滤器链、异常兜底）。Java 的 Servlet Filter、Spring Security 的过滤器链都是责任链。

### 7. 熔断器（Circuit Breaker）

**是什么**：一个服务连续失败达到阈值，就「断开」一段时间，期间请求直接失败或走兜底，不再打过去；过一段时间放少量请求试探（半开），成功就恢复。三个状态：**关闭（正常）→ 打开（熔断）→ 半开（试探）**。

**为什么需要**：如果某个模型挂了，每个请求都要先重试 3 次（几十秒）才换兜底模型，用户体验很差，还占着连接。熔断后直接跳到兜底模型。

**项目里怎么用**：`core/llm/breaker.py`，和兜底链配合。

**Java 对应**：Hystrix、Sentinel、Resilience4j。

### 8. 生产者-消费者 / 发布订阅

**是什么**：生产者只管往队列里放，消费者只管从队列里取，两边通过队列解耦，速度可以不一致。

**项目里怎么用**：Agent 生成（生产者）→ Redis Stream（队列）→ SSE 推送（消费者）。好处：用户刷新页面只是换了个消费者，生产不受影响；多个页面可以同时看同一个对话。Celery 也是这个模式。

### 9. 拦截器 / 钩子（Interceptor / Hook）

**是什么**：在某个动作前后插入统一的处理逻辑，不改动作本身。

**项目里怎么用**：工具执行前的 `pre_tool_hook`（可以改参数或拒绝）、打转检测（执行前判断是否重复）、工具执行后统一拼接「经验提示」。Flask 的 `before_request`、Java 的 Spring AOP 都是这个思路。

### 10. 插件化 / 可插拔（Plugin）

**是什么**：主程序定义好扩展点和接口，新能力以插件形式「插上」即可生效，不改主程序。

**项目里怎么用**：
- **Skill**：往目录里放一个 `SKILL.md`，Agent 就多了一项技能；
- **MCP**：配置文件里加一个 MCP server，它的工具就自动注册；
- **子 agent**：注册一份配置就能被主 agent 委派。

**旧项目里**：大模型智能助手平台的「可插拔组件」也是这个思路。

### 11. 装饰器（Python 语法）与装饰器模式

Python 的 `@decorator` 是语法糖，本质是「函数包一层函数」；设计模式里的装饰器模式是「对象包一层对象，增强功能但接口不变」。两者思路相同。项目里：`@login_required`（鉴权）、解析流水线的 `@notify(step_name)`（每步自动上报进度）。

## 二、Agent 与大模型

| 词 | 是什么 | 项目里 |
|---|---|---|
| **Agent 运行时** | 驱动模型「思考 → 调工具 → 看结果 → 再思考」循环的程序，以及围绕它的上下文、工具、取消、压缩等机制。也叫 harness | `core/agent/orchestrator.py` |
| **单循环 / 主循环** | 整个 Agent 就是一个循环：请求模型，模型要调工具就执行并把结果回填，不调了就结束 | 见 01 文档 4.3 节伪代码 |
| **Function Calling / Tool Use** | 模型按 JSON Schema 输出结构化的工具调用，由程序执行，结果再喂回模型 | 所有工具 |
| **子 agent** | 主 agent 把一个子任务交给另一个独立上下文的 agent 去做，只拿回结论，不污染主上下文 | `tools/agent_tool.py` |
| **MCP** | Model Context Protocol，Anthropic 2024 年底提出的工具接入标准协议 | 接入企业信息查询服务 |
| **Skill** | 一个目录 + `SKILL.md`，写着做某类事情的方法和脚本；平时只露名字，用到时才读全文 | 生成 Word / PPT / Excel / HTML |
| **CLI 连接器** | 把飞书、企微、CRM 等外部系统包装成命令行工具，Agent 在沙箱里调用 | lark / wecom / xbb / mes 等 |
| **上下文工程** | 决定每一轮让模型看到什么：放什么、什么时候放、怎么省、怎么隔离 | prompt 分层、按需加载、压缩、子 agent |
| **Prompt 缓存** | 供应商缓存请求的公共前缀，命中部分大幅降价、首字更快；前缀变一个字就失效 | 分层 prompt 结构，缓存命中率约 35% → 90% |
| **上下文压缩** | 对话快超出模型窗口时，把旧历史总结成摘要，保留最近几轮 | 下一次请求超窗口 85% 触发 |
| **工具按需加载** | 低频工具平时只给名字不给参数说明，模型搜索后才激活 | deferred + ToolSearch |
| **打转检测** | 发现模型反复用几乎相同的参数调同一个工具，先提醒、再拦截 | 按工具名分桶 + 近似重复判定 |
| **Memory 分层** | 不同性质的信息存在不同地方、用不同方式注入 | 见下表 |
| **模型网关层** | 所有模型调用的统一入口，屏蔽供应商差异，集中做限流、计费、重试、兜底、熔断 | `core/llm/client.py` 的 `LLMClient` |
| **动态切换 / 热生效** | 模型和参数存在数据库里，配置中心改完下一次请求就生效，不用发版 | AI 配置中心（gateway） |
| **SSE** | Server-Sent Events，服务端通过一个 HTTP 长连接持续往浏览器推消息，单向 | 对话流式输出 |
| **断线重连重放** | 事件存在 Redis Stream 里，重连时从头读一遍，前端从头渲染 | `completion_stream.py` |
| **进程内无状态** | 任何需要跨请求保留的状态都放 Redis / PG，不放进程内存，所以任意副本都能处理任意请求 | 多副本部署的前提 |
| **水平扩展** | 加机器 / 加副本来提升处理能力（对比垂直扩展：换更强的机器） | Docker Swarm 多副本 |
| **分级控制（取消 / 停止 / 插话）** | 取消 = 整个作废；停止 = 这一轮到此为止，结果保留；插话 = 生成中追加一句，下一轮模型能看到 | 01 文档 5.9 节 |

**Memory 分层（简历里那条的展开）**

先对上业界通用的说法（简历用的是这套词）：

| 业界术语 | 含义 | 我们对应的记忆 |
|---|---|---|
| 短期记忆（Short-term / Working） | 当前会话里的上下文 | 消息历史、压缩摘要、对话笔记 |
| 长期 · 语义记忆（Semantic） | 事实和知识 | 项目记忆、组织画像、企业经验、知识图谱事实 |
| 长期 · 程序性记忆（Procedural） | 怎么做事的经验和规则 | 工具习惯（工具用法、偏好、资料去向） |
| 长期 · 情景记忆（Episodic） | 过去发生过的具体经历 | 历史会话摘要（我们用得少，可不主动提） |

- **Mem0**：开源记忆层，核心流程是「对话后用模型抽取候选记忆 → 和已有记忆比对，决定新增 / 更新 / 删除 / 不变 → 检索时按相关性召回」。我们的项目记忆就是这个流程（已有内容变了就更新那一条，不重复新增）。
- **LangGraph**：把记忆分成线程内的短期记忆（checkpointer）和跨线程的长期记忆（store，按 namespace 隔离），我们按个人 / 组织 / 项目隔离是同一个思路。
- **Letta（原 MemGPT）**：把上下文窗口当「内存」、外部存储当「硬盘」，由 Agent 自己调工具在两者之间换入换出 —— 对应我们的「工具召回」。

下面是项目里的具体设计：

入层判据（三个问题）：
1. **会不会变？** 不变的事实 → 知识图谱；会变的偏好、约定 → 记忆表。
2. **需不需要关系查询？** 需要「从 A 走到 B」→ 图谱（这是图唯一不可替代的能力）；只要读出来贴进 prompt → 记忆表。
3. **谁写的？** 系统从资料里自动抽取 → 图谱（带置信度、可重新抽取）；用户明说的、Agent 从失败里学的 → 记忆表。

| 记忆 | 内容 | 怎么来 | 怎么注入 | 归属 |
|---|---|---|---|---|
| 工具习惯 | 工具怎么用不出错、同类任务偏好哪个工具、该去哪找资料 | 对话后异步学习；用户也可手动记录 | 偏好**常驻**；工具用法「**目录 + 召回**」（第一次用某工具时附上经验目录） | 个人 / 组织 |
| 项目记忆 | 项目里已经说定的决策、事实、约定 | 项目对话每轮结束后异步提取，每次最多 5 条，必须能指到原话 | 目录（最多 15 条摘要）+ 按需展开 | 项目 |
| 组织画像 | 组织是谁（行业、规模、业务） | 管理员填写优先；上传资料后汇总 | 工具召回 | 组织 |
| 企业经验 | 术语、指标口径、流程 | 生成候选，经审核 | 工具召回 | 组织 |
| 事实 | 人、组织、事件及其关系 | 对话后 / 资料上传后抽取到 Neo4j | 工具召回 | 组织 |

**三种注入方式**：
- **常驻**：每次对话都放进 prompt（只放最小、最常用的）；
- **目录 + 召回**：先给标题和一句话摘要，模型觉得相关再用工具展开全文（渐进式披露）；
- **工具召回**：完全不预先给，模型需要时自己查。

**为什么异步**：记忆提取要额外调一次模型，放在对话结束后的后台任务里，不让用户等。

**安全点**：目录里的文字会去掉特殊符号、限制长度，防止一条记忆变成影响其他成员的「指令」（记忆注入攻击）。

## 三、RAG 与知识

| 词 | 是什么 | 适合 / 注意 |
|---|---|---|
| **RAG** | Retrieval-Augmented Generation，先检索相关资料，再让模型基于资料回答 | 解决模型不知道企业私有知识、减少幻觉 |
| **Agentic RAG** | 检索作为一个工具交给 Agent，由模型决定查不查、查几次、换什么关键词 | 比「每次固定先检索一次」灵活；我们用的是这种 |
| **文档解析** | 把 PDF / Office / 音频 / 图片转成文本（markdown）| 难点：表格、扫描件（OCR）、图片里的文字、音频转写 |
| **切分（Chunking）** | 把长文档切成小段再向量化 | 太大检索不准，太小丢上下文；常见按标题结构 + 长度切，带重叠 |
| **向量化（Embedding）** | 用模型把文本转成一串数字（向量），语义相近的文本向量也相近 | 换 embedding 模型要全量重建索引 |
| **稠密向量检索** | 按语义相似度找（余弦相似度） | 擅长同义表达；**不擅长精确匹配**（型号、编码、人名） |
| **BM25 / 稀疏向量** | 传统关键词检索算法，看词频和逆文档频率 | 擅长精确匹配；不懂同义词 |
| **混合检索** | 两种一起查，再融合排序 | 互补；我们在 Qdrant 里同时存稠密向量和 BM25 稀疏向量 |
| **RRF** | Reciprocal Rank Fusion，按排名融合：`score = Σ 1/(k + 排名)`，k 通常取 60 | 不需要两种分数在同一量纲，简单稳健 |
| **重排序（Rerank）** | 先粗召回几十条，再用一个更准但更慢的模型对「问题 + 每条结果」逐一打分重排 | 准确率明显提升；成本是多一次模型调用 |
| **权限过滤** | 检索时按 payload 过滤（个人 / 组织 / 项目可见范围） | 必须在**检索时**过滤，而不是检索后再删（否则可能召回结果全被删光） |
| **知识图谱** | 实体（节点）+ 关系（边）组成的网络，存在 Neo4j | 适合关系类问题（谁负责什么、A 和 B 什么关系） |
| **图谱抽取** | 用模型从文本里抽取实体和关系写入图谱 | 难点：实体去重（同一个人不同叫法） |
| **Text2Cypher** | 用模型把自然语言问题转成 Cypher 查询语句 | 要限制只读、加超时、加 LIMIT |
| **渐进式披露** | 先给目录 → 再给摘要 → 最后给全文 | 我们的知识库工具就是这三步 |

## 十、旧项目里的概念

| 词 | 是什么 | 适合 / 注意 |
|---|---|---|
| **BPMN** | 业务流程建模标准，用图描述流程（开始、任务、网关、结束），引擎（Camunda / Flowable）按图执行 | 智能助手平台用来编排大模型应用流程；适合审批流、固定业务流 |
| **可插拔组件** | 每个能力做成符合统一接口的组件，按需组合 | 见设计模式第 10 条 |
| **JSON Schema** | 用 JSON 描述 JSON 数据结构的标准（字段类型、必填、取值范围） | 采编平台用它适配多变的内容结构；**大模型的 function calling 参数定义用的也是 JSON Schema**，可以借这个点把老经验和 AI 联系起来 |
| **SSO 单点登录** | 一次登录访问多个系统（CAS、OAuth2、OIDC） | 采编平台；现项目的 OEM 合作方也走 SSO |
| **RBAC 权限系统** | 用户 → 角色 → 权限 | 采编平台新增的权限系统 |
| **物理多租户 vs 逻辑多租户** | 物理：每个租户一套库 / 表，隔离好但冗余大、扩容难；逻辑：所有租户共用表，用 `tenant_id` 区分 | 内容服务平台从物理改逻辑；现项目也是逻辑多租户（按组织 / 用户过滤） |
| **规则引擎** | 把业务规则从代码里抽出来变成可配置的规则（条件 → 动作） | 内容服务平台自研的轻量规则引擎；对应现在的「配置中心热生效」思路 |
| **VuePress** | Vue 驱动的静态站点生成器 | 个人博客 |
| **Cloudflare** | CDN + DNS + 安全代理 | 博客代理 |
